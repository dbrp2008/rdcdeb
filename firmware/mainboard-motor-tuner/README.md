# MainBoard Motor Tuner (TR enabled; AR disabled pending verification)

This is an **independent STM32F405 MainBoard firmware project** for bench characterization. It does not compile or replace either robot's normal-control application or communicate with the Controller. The IOC, CubeMX-generated `Core/` and `Drivers/` folders are directly in this project root. Hand-written tuner code, display support, CAN-specific HAL files, startup/linker files and the custom CMake build system are kept in `App/` and `buildsystem/` so they are separate from the standard generated folders. The checked-in generated baseline was copied from the MainBoard project because its configured SPI, UART, DMA and GPIO peripherals match this IOC; regenerate with STM32CubeMX and verify that the generator leaves `App/` and `buildsystem/` untouched before relying on this layout. The MainBoard project files are not used as CMake source paths and must not be modified for this tuner.

## Profile and operation

- The enabled profile is **TR / 3 motors**. TR motor 1 (ESC ID 1) and motor 2 (ESC ID 2) use CAN1; motor 3 is the **trailing motor**, keeps ESC ID 3, and uses CAN2 only. The two CAN networks are independent; never bridge them. Hold BTN1 for about 0.9 seconds to cycle the TR motor. The **AR profile is disabled in firmware** (`TUNER_PROFILE_AR_ENABLED=0`) because its motor/controller interface is unverified and may not be CAN. Do not enable AR until its protocol and limits are confirmed and a matching backend is implemented/tested.
- Press BTN2 to start a run; press BTN2 again to abort. The motor under test alone is commanded; all other motor-current setpoints are zeroed.
- Each run waits for fresh feedback and speed at or below 2 output RPM for 250 ms before each phase. It performs three brief current pulses (0.25 A, 0.50 A, 0.75 A; 250 ms each), then repeats 2-second PID trials at the 4,000 motor-RPM target (about 211 output RPM at 19:1), using a sequential P→I→D search: first Kp is adjusted for rise/overshoot with Ki=Kd=0; after the first acceptable P response, it tests up to two successively lower Kp values with 5–20% adaptive steps and restores the last passing Kp when a fine step fails before entering I, then Ki is added only to remove steady-state error and only when normalized ARPM/TRPM ≥0.95, and Kd is introduced only if measured overshoot needs damping. It can flow backward: overshoot after adding I reopens P, and D-related slow rise or accuracy loss reopens P or I. During a P backtrack it preserves the partially successful I (and reduced D when applicable) instead of clearing learned gains and retuning them from zero. Every failed trial changes the gain vector before the next run; Kp, Ki, and Kd use dynamic leaps: Kp steps range 10–50% (5–20% in fine search), Ki steps range 0.001–0.006 based on steady error, and D steps range 0.0001–0.0008 based on overshoot. Once actual RPM drifts by no more than 3% of target over 300 ms, it records ARPM/TRPM for diagnostics only; the target is not scaled by the ratio or its inverse. Per-sample CSV includes ARPM/TRPM ×1000 and a `#RATIO` calibration record. The search refines one live gain set instead of cycling through six preset candidates, reducing redundant trials. It has no fixed trial count: it stops after three consecutive trials satisfy the relaxed acceptance limits (10–90% rise ≤500 ms, overshoot ≤8%, final error ≤3%, with that accuracy held for 300 ms), or earlier on fault / B2 abort. It requires zero-current settling between phases, at least 1 second rest and ESC temperature below 50 C before a new phase; failure to settle/cool within 5 seconds faults. The software current ceiling is 5.0 A; limits and gain bounds are in `App/Core/Inc/motor_tuner_config.h` and `App/Core/Src/motor_tuner.c` (Kp ≤0.225, Ki ≤0.045, Kd ≤0.0045).
- USART2 CSV samples include both commanded and ESC-reported current, target and measured output RPM, temperature, Kp/Ki/Kd, rise time, overshoot, steady-state error, and pass streak. A `TRIAL` row summarizes each trial; after three consecutive passes, a `RESULT` row reports the accepted Kp/Ki/Kd and readings. Kp/Ki are scaled by 1,000; Kd by 1,000,000. The TFT retains the accepted result.
- CSV samples are sent at 50 Hz over USART2 (115200 8-N-1); connect a 3.3 V USB-UART adapter and capture the output to a CSV file. Logs distinguish commanded current from ESC-reported motor current and include ESC temperature. The TFT shows the selected profile/motor, phase state (including settling/fault), target/actual speed, commanded/reported current, gains, integral absolute error and peak speed.
- The accepted gains are only the best observed tuning candidate under these thresholds; they are not proof of stability under all loads. The tuner does **not** save or deploy gains to either robot. Review the full log and validate the accepted gains under the actual load before porting them to separate firmware.

## Motor setup checklist (read before applying motor power)

1. **Identify the hardware first.** Record each motor model, its matching ESC/controller, rated voltage/current, gearbox ratio, connector, and intended chassis position. The TR preset assumes three RM-style C620 CAN motors. The AR ID placeholders do **not** prove AR hardware is RM/C620-compatible. The AR profile is disabled by default; do not enable or run it until the actual motor/controller interface, protocol and ratings are confirmed and a matching backend is implemented.
2. **Secure the mechanical setup.** Fix the board and motor securely, check the gearbox/wheel/drive train turns freely with power off, clear loose objects, raise the drive wheels off the ground, and keep people clear. Keep a physical battery/power disconnect within reach. Never rely on BTN2 or firmware abort as an emergency stop.
3. **Verify the motor map and IDs.** Before powering the motors, map each physical motor to its CAN ID and direction. Edit `App/Core/Inc/motor_tuner_config.h` to match the TR C620 ESC IDs (`TUNER_TR_MOTOR_*_CAN_ID`). IDs must be in 1–8 and unique on each bus. The configured map is ESC IDs 1/2 on CAN1 and the trailing motor's unchanged ESC ID 3 on CAN2 only; the same ID could exist on a separate bus. The AR ID macros are placeholders only; AR is compile-time disabled (`TUNER_PROFILE_AR_ENABLED=0`) and must stay disabled until the actual interface is identified and supported. Hold BTN1 for about 0.9 s to advance the TR motor. Confirm the TFT profile and motor index before pressing BTN2.
4. **Check CAN wiring and settings.** Verify CAN-H/CAN-L polarity, common ground where required by the hardware, connector pinout, suitable termination at the bus ends, and 1 Mbit/s bitrate at both ends. With motor power disconnected, inspect continuity and ensure there is no short between supply, CAN, and ground. Do not connect CAN pins to UART pins.
5. **Confirm the speed convention and reduction.** The code assumes a 19:1 reduction (19 motor-shaft turns per output-shaft turn) and divides CAN-reported motor-shaft RPM by 19; targets and displayed/logged speed are output-shaft RPM. Confirm the fitted ESC actually reports motor-shaft RPM and that this ratio applies to the selected motor. If not, change `TUNER_GEAR_RATIO_MOTOR_TO_OUTPUT` or the feedback conversion before tuning; do not use one profile's ratio for another motor without verification.
6. **Validate current limits against the weakest component.** The PID current command is software-clamped at 5.0 A, while the initial characterization steps are 0.25, 0.50, and 0.75 A. Verify the motor, ESC, supply, wiring, and gearbox can safely support the chosen cap; if any rating is lower, reduce the software cap before connecting power. Use a supply with its own current limit. A software cap is not hardware protection.
7. **Test with the full drivetrain connected.** Separate motor/ESC connections are not required, but the entire mechanism must be secured, wheels clear, current-limited, and monitored. Hold BTN1 about 0.9 s to select the motor, verify the TFT motor/bus assignment, then press BTN2 only when ready. This test commands the selected motor while commanding zero on other channels; zero is not an emergency stop. Keep a physical disconnect within reach and stop for unexpected motion, noise, heat, or stale feedback.
8. **Save the USART2 capture.** It emits CSV at 50 Hz with commanded/ESC current, target/actual RPM, and tuning metrics. `TRIAL` rows report every 2-second attempt and whether it met the strict limits; `RESULT` appears after three consecutive passes and lists accepted Kp/Ki/Kd. Press B2 to abort at any time; the tuner has no fixed attempt limit but still stops on safety faults. The tuner does not save or deploy gains automatically.

## Hardware assumptions and bounds

- The current motor backend assumes RM-style C620 CAN current commands and RM feedback frames, with CAN1 at 1 Mbit/s for IDs 1/2 and CAN2 at 1 Mbit/s for trailing motor ID 3 only (MCU pins PA11/PA12 and PB12/PB13 respectively). The local CAN HAL source/header are from the same STM32F4 HAL 1.8.5 release as the base MainBoard HAL. The AR's exact motor/ESC is not confirmed. The team has reported that AR may use a non-CAN interface; this is not yet confirmed. AR is disabled in code by default. If it uses a different interface, implement and validate a matching backend before any AR tuning; the profile count or CAN-ID macros do not make an incompatible controller tunable.
- The CAD material folder in Google Drive includes an RM-M3508 and six-inch omni wheel, but those are not proof of the final TR build. Verify the assembled motors, ESCs and IDs and update the profile map before connecting motor power.
- Per-motor requested current is capped at 5.0 A; the PID target is 4,000 motor-shaft RPM (about 211 gearbox-output RPM at 19:1); the command ceiling and overspeed trip are 4,370 motor-shaft RPM (230 output RPM safe ceiling). A run aborts for missing/stale feedback, speed above the threshold, or motor temperature at/above 70 C. CAN velocity feedback is interpreted as motor-shaft RPM and divided by the 19:1 reduction; confirm that convention for the fitted controller. The application sends zero-current commands for all eight RM channels at boot, while idle, after abort and after a completed run. While idle, a CAN transmit queue error shows `TX:ERR` but does not block motor selection or the TFT controls. During a run, a transmit error latches `FAULT`; missing/stale feedback, overspeed, overtemperature, and settle timeout also lock out further runs until reset. Do not start a test while `TX:ERR` is shown. Use the physical disconnect when needed; zero current is not active braking. The 5 A software ceiling is not a substitute for hardware current limiting or a physical emergency stop. A `FAULT` state prevents another run until reset; identify and correct the cause with motor power disconnected before resetting. A zero-current command is not an active brake and does not guarantee the motor has stopped.
- Secure the robot, clear the wheels, use a current-limited supply, and keep a reachable physical power disconnect. Begin with motor power disconnected while verifying the firmware and CAN wiring. Do not run with people or loose objects near moving wheels.

## Build

Use the same GNU Arm Embedded toolchain version already required by the RDC workspace (GNU 14.3.1+st.2); do not change system PATH or remove other installed compiler versions. The CMake presets are `Debug` and `Release`:

```sh
cd buildsystem
cmake --preset Debug
cmake --build --preset Debug
```

Open the motor-tuner folder (or the repository’s `RDC-Firmware.code-workspace`) in VS Code and use **Terminal → Run Task** to select `CMake: Build Motor Tuner Release`, `Flash Motor Tuner via ST-LINK`, or `Build + Flash Motor Tuner (Release)`. The combined task builds before flashing. The build uses the Release preset from `buildsystem/`; tasks do not run CubeMX generation. Open the root `motortuner.ioc` in STM32CubeMX. Generated peripheral files live in the project-root `Core/` and `Drivers/` folders. The hand-written firmware is separated under `App/`, and the custom CMake build files live under `buildsystem/`, so they are not stored alongside the generated peripheral sources. The IOC has `ProjectManager.DeletePrevious=true`; generation behavior with this root-level layout has not yet been tested here. After generation, confirm CubeMX did not alter `App/` or `buildsystem/` before building. The generated `Core/Src/main.c` is intentionally not compiled; the application uses `App/Core/Src/main.c`. CMake fails early if key generated files are absent. Use the `buildsystem/` CMake presets or the VS Code motor-tuner tasks for the actual tuner application. The CubeMX-generated root `CMakeLists.txt` currently builds CubeMX's template `Core/Src/main.c`, not the custom `App/Core/Src/main.c`; do not treat that generated target as the tuner firmware. Its root CMake presets are isolated under `build/cubemx-template-*`. The VS Code tuner tasks use `buildsystem/` and produce the actual tuner at `build/Release/MainBoardMotorTuner.elf`. The target firmware must be built and linked with the required GNU 14.3.1+st.2 toolchain after any IOC regeneration. Do not run a motor experiment until the target build succeeds and the exact TR hardware is verified. AR stays disabled until its interface is confirmed and supported.
